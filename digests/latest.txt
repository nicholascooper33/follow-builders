The Secrets of Claude's Platform From the Team Who Built It
AI & I by Every
https://www.youtube.com/watch?v=lLypHkIVLqc

The Anthropic platform team's core vision is simple: get the best outcome out of Claude with as little developer work as possible — and they're building the infrastructure so you don't have to rebuild it yourself.

In this episode of AI & I (Every), host Dan Shipper sits down with Angela (Head of Product for the Claude platform) and Caitlin (Head of Engineering for the Claude platform) to unpack how Anthropic thinks about the platform layer above its models, and what it means for developers building agents today.

The conversation traces the arc from the earliest completion endpoints to Claude Managed Agents, where the platform now provides persistent state, built-in tools (code execution, web search, file systems), and production-grade cloud infrastructure. Angela describes the through-line across all of these iterations: "As Claude continues to get better and more autonomous, we find ourselves basically needing to evolve the platform to be higher and higher order abstraction — in pursuit of making things literally as easy as possible."

A key theme is model lock-in. Angela argues that the older strategy of building a fully generic harness you can hot-swap between providers is increasingly a false economy. As each lab takes distinct approaches to advancing its models, the harness and the model become more tightly paired. "For the next generation of models, the harness and the model get very paired. You still need redundancy, and you still might want to use other models for things — but the way you think about it changes."

Caitlin explains that Managed Agents was born directly out of Anthropic's own pain building internal products: "We did stand up the infrastructure so that it works well enough times that we ourselves were like, okay, we're done building this for ourselves. We're doing it once in a way that's gonna really work from everything that we've learned." She also addresses the worry that Managed Agents will lag behind Claude Code in new features — Anthropic's internal products run on the same platform as external customers, which creates a strong incentive to close any gaps quickly.

Direct quote — Angela on the platform's future: "We wanna experiment with directions where Claude actually gets so good at understanding itself — it figures out what model you should be using, it figures out how to spin up all the sub agents. You don't have to think so much about what architectures there are, because Claude is actually able to understand itself enough that it can write itself on the fly."

The episode is worth watching in full for anyone deciding what level of abstraction to build on: the raw messages API, Claude Managed Agents, or something in between.

An update on recent Claude Code quality reports (Anthropic Engineering)
https://www.anthropic.com/engineering/april-23-postmortem

Anthropic published a detailed postmortem on three separate issues that caused Claude Code, the Agent SDK, and Claude Cowork to regress for some users over the past month (the API was not affected). The three root causes: (1) Claude Code's default reasoning effort was quietly downgraded from high to medium in March to reduce UI-freezing latency — the wrong tradeoff since users preferred intelligence over speed; it was reverted April 7. (2) A bug caused Claude's thinking state to be cleared every single turn for idle sessions instead of just once, making it seem forgetful and repetitive; fixed April 10. (3) A third issue affected Claude Cowork. All three were resolved as of April 20 (v2.1.116). The post includes a forward-looking section on what Anthropic will do differently to prevent silent regressions.

Built-in memory for Claude Managed Agents — public beta (Anthropic)
https://claude.com/blog/claude-managed-agents-memory

Anthropic launched built-in memory for Claude Managed Agents in public beta. Agents can now learn and carry knowledge across sessions using a memory layer optimized for long-running, multi-session workflows. Memories are stored as files on a mounted filesystem, so developers can export them, manage them via the API, and keep full programmatic control. Memory stores can be scoped per-user or org-wide (with different read/write permissions), shared across multiple agents, and accessed concurrently without overwriting conflicts. Enterprise deployments get scoped permissions, audit logs, and full API control. The filesystem-based design means Claude relies on the same bash and code execution tools it already uses — no new mental model required.
